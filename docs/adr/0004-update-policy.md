# ADR 0004 — 只在语义需要时重写正文（P0–P4）

- 状态：已采纳
- 相关：`src/domains/story/policy.mjs`、docs/pipeline.md

## 背景

最初每次更新都全量重写 Story。两个后果：

1. **丢信息**：一次重写把 5,400 字的报道压到 4,000 字，覆盖率 68%，还没有回滚；
2. **烧钱**：一天几十次重写，成本与延迟都不可接受。

## 决策

先分级，再决定动不动正文：

| 级别 | 触发 | 动作 |
|---|---|---|
| P0 | 撤回 / 矛盾 / 主体否认 | 全量重写 + supersede |
| P1 | 主线变化（标题重叠 ≥0.45 且命中状态词，或 lede 判定 ≥0.55） | 定向重写或拆篇 |
| P2 | 追加节 ≥2 且追加比例 >0.30 且缺口 ≥ max(6, facts×5%) | 先节合并，不行再重写 |
| P3 | 有缺口但不改主线 | 追加一节 |
| P4 | 无实质缺口 | 不动，只记 `story_update` |

配套门禁（覆盖 / 长度 / 重复 / 受影响小节），任何一条不过 → 降级为追加。

## 后果

- ✅ 信息不再静默丢失（门禁 + 追加兜底 + 快照回滚）；
- ✅ 成本下降一个数量级；
- ✅ `story_update` 成为可回放的决策日志；
- ⚠️ 规则多，需要真实更新回归（`cli/policy-regression.mjs`）；
- ⚠️ P1 的关键词启发式会误判，靠标题重叠阈值压到 ~2/10。

## 备选

| 方案 | 为什么不选 |
|---|---|
| 每次重写 | 丢信息 + 贵，已实测 |
| 永不重写，只追加 | 几个月后 Story 变成追加日志，不可读 |
| 全交给 LLM 判断 | 不可复现、不可解释、无法调参 |
