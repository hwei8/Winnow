# 个人信息系统 Design Proposal（v0.2）

> **定位**：一套给人用的记忆与信息过滤系统。记录"我知道什么、我想知道什么、我已经看过什么"，然后只把这个状态往前推的东西送到你面前。
> **形态**：IM 简报（有限推送）+ Web（无限拉取，可浏览记忆）。
> **预算假设**：LLM 不是瓶颈（≈10B tokens/月，可追加）。
> **配套文档**：[DECISIONS.md](DECISIONS.md)（已拍板决策）、[SCHEMA-DRAFT.md](SCHEMA-DRAFT.md)（结构化记忆模型）。

---

## 1. 需求 → 三个接口，一个状态

| # | 需求 | 系统里的接口 |
|---|---|---|
| 1 | 记忆我想记的东西 | **写**：capture + 结构化 claim |
| 2 | 主动抓我想看的 | **推**（IM 简报）/ **拉**（Web 无限流） |
| 3 | 屏蔽已知/重复 | **差集**：候选 vs 我的知识状态 |

三条共用一个底座：**Knowledge State**（我知道什么 + 我在意什么 + 我看过什么）。

```
                    ┌─────────────────────────────┐
                    │      Knowledge State         │
                    │  claim / story / entity      │
                    │  known 水位 / stance / 标注   │
                    └───┬──────────┬──────────┬───┘
             写 ▲        │ 读        │ 比        │ 比
                │        │          │          │
          ┌─────┴──┐ ┌───┴─────┐ ┌──┴──────┐
          │ ①记忆   │ │ ②推 IM   │ │ ②拉 Web  │
          │ capture │ │ 简报12条 │ │ 无限流   │
          └────────┘ └─────────┘ └─────────┘
                        ▲ 差集：③去重/新颖度（驱动两者）
```

## 2. 设计原则（v0.2 修订）

1. **人类可读、可改、可删**：每条记忆能一跳回到原文；系统对"你已知"的判断你可推翻。
2. **声明优先，行为为辅**：兴趣来自显式声明（主题/源/反例），行为只调排序，不定义你是谁。
3. **稀缺性只约束 push**：IM 有硬配额；Web 允许无限，但必须给"有限性信号"（见 §7.2）。
4. **每条推送必须回答「新在哪 / 为什么推你」**：答不上来不推。
5. **LLM 是理解和维护的工人，不是事实的权威**：claim 必须带原文子串证据，无证据降级 `unverified`。
6. **本地优先、可导出**：SQLite + 文件，Markdown/JSON 一键导出；数据所有权不外包。
7. **失败必须可见**：能回答"这条为什么没推""我上周漏了什么"（`decision_log`）。
8. **不优化停留时长**：排序目标是信息增益与深度可用性。任何"让你多待一会"的机制都不做。
9. **反茧房是硬约束**：固定"分歧/长尾"槽位 + "必达"通道（钱/健康/安全/在做的项目）。
10. **记忆会腐烂，需要防腐**：外部知识有验证有效期；私人记忆不过期但需要"在对的时候被再次看到"。
11. **结构化优先**：能进字段的绝不塞进文本；结构化不了的退化为自由文本 + 标注 `extraction_method`。
12. **模式可演化**：本体不追求一次设计完美，靠 LLM 提议 + 人工批准 + 历史回填持续演进。

## 3. 编辑部架构：从"管线"到"常驻编辑"

因为 token 不再是瓶颈，架构从"省钱的漏斗"升级成**一家只有你一个读者的新闻编辑部**。

| 角色 | 职责 | 频率 | 预算/次 |
|---|---|---|---|
| **Collector** | 跑 adapter，拉条目、归一化、去重、抽正文/字幕 | 每 15–60 分钟 | ≈0（无 LLM） |
| **Story Editor** | 每个活跃故事一个常驻编辑：维护规范化页面、合并复述、抽取 claim、登记 delta、更新 novelty_frontier | 有新条目即触发 | 10–15k |
| **Fact Checker** | 双模型交叉 + 原文子串校验；冲突检测；过期重验证；处理你的"这条错了"标注 | 常驻/夜间 | 8k |
| **Beat Reporter** | 每个声明兴趣一个跑口记者：扫源、找缺口（"这件事你只知道头条"）、发现你应该关注但没订的源 | 每天/每周 | 20k |
| **Chief Editor** | 每天从 story_update 里选 12 条，分配通道，写"为什么推你"，写简报 | 每天 1 次 | 50k |
| **Librarian** | 整理 capture：归类、关联实体/故事、安排回访时间、发现"存了没看" | 每天 | 15k |
| **Researcher** | 按需深度报告（时间线/多源对照/反方观点） | 你点的时候 | 200–800k |
| **Ontologist** | 提议新谓词/新实体类型、合并重复实体、回填历史 claim | 每周 | 100k |

**关键设计**：每个 agent 的产出都是**对结构化表的写入**，不是只往聊天里回话。这样"编辑器"的成果是持久的、可浏览的、可审计的。

## 4. 概念模型（详见 SCHEMA-DRAFT.md）

```
Source(源) → Item(条目) → Story(事件) → Claim(主张) → Entity(实体)
                              │            │
                              └── Story Update（"自你上次看新增了什么"）
                                           │
              Knowledge State（水位/标注/stance）←── 你
```

**四层为什么必须分开**

- **Item → Story**：解决"同一件事一万篇"。Story 才是你的阅读单位。
- **Story → Claim**：解决"不同文本、相同主张"。Claim 是差集的计算单位。
- **Claim 双时间轴**：`world_from/to`（世界何时为真）、`asserted_at`（源何时说）、`recorded_at`（我们何时知道）、`superseded_at`（何时失效）。少了这套，"记忆"退化成"最后一条覆盖前一条"。
- **Entity**：让浏览成为可能——"关于这家公司我知道的一切"必须能一次列出来。

**两个空间**：`capture`（私人：想法/决策/生活，不去重、不过期）与 `claim`（外部事实，去重、会腐烂）。两者通过 `capture_link` 双向关联。

## 5. 去重：三层漏斗（v0.2：不再需要省钱式预筛）

| 层 | 手段 | 砍掉什么 | LLM |
|---|---|---|---|
| L1 | URL 归一 + 正文指纹 + simhash | 转载/镜像/聚合 | 不用 |
| L2 | 向量召回 + 聚类（每篇都抽 claim 后按主张重叠聚类） | 同事件的多篇报道 | 用，但便宜 |
| L3 | Claim 差集 vs `knowledge_state` | 文本不同、主张相同的复述 | 用，全量 |

**什么算"新"**（任一为真才进入简报；Web 可展示但不占位）

| 新在哪 | 权重 |
|---|---|
| 新主张 / 新数字 | 高 |
| 主张被修正、反驳、撤回 | **最高（永远放行）** |
| 源等级提升（自媒体转述 → 官方/一手） | 高 |
| 新主体加入（监管、第三方） | 中 |
| 实质进展（不是"持续关注"） | 中 |
| 深度分析（解释为什么，而非复述是什么） | 中（按你的深度偏好） |
| 纯观点 / 纯情绪 / 蹭热点 / "三点启示" | 0，丢弃 |

**冗余经济**：每个 Story 每天曝光预算 `1 一手 + 1 分析 + 1 反对`，其余 `folded` 进时间线——信息不丢，但不占你的注意力。

**屏蔽五层**：源 / 作者 / 主题（带期限）/ **表述模式**（"震惊体""三点启示体"，正则先于 LLM）/ 事件疲劳（同一 Story 超 N 条/天软静默）。

## 6. 推：IM 简报（有限）

```
今日简报 2026-11-10      预计 8 分钟 / 12 条 / 3 件事有更新

■ 必看（不可被兴趣挤掉）
 1. [事件] 某芯片厂复产，良率低于预期
    新在哪：首次出现"良率"数据（此前你知道"已复产"）
    为什么推你：你关注半导体产能；关联你 3 个月前存的采购决策
    来源：官方公告 + 2 篇分析（4 篇复述已折叠）
    [我知道了] [别再推这个] [写点什么]

■ 兴趣
 2. …

■ 探索（今天的分歧视角）
 9. [观点] 关于 X 的主流叙事可能算错了…
    为什么推你：与你已存的主张「…」矛盾

■ 我自己存的
 - 2 天前你记的：「…」今天这件事和它有关
```

**三通道配额**：必达 1–3 / 兴趣 主体 / 探索 1–2（强制，不可被兴趣挤占）。

**每条固定回答**：发生了什么 / 新在哪 / 为什么与你有关系。三个问题任一答不上来，就不该进简报。

## 7. 拉：Web（无限流 + 记忆浏览）

### 7.1 无限 ≠ 无底洞：三个下探轴

主流信息流的"无限"是**卡的无限**。这里的"无限"是**知识深度的无限**：

| 轴 | 说明 |
|---|---|
| **广度** | 继续往下滚 = 更多故事，按 gain 递减，并显式分区（`以下优先级更低` / `以下是你 7 天前错过的` / `以下是相邻但你未声明的兴趣`） |
| **深度** | 同一张卡展开：L1 一句话 → L2 主张与证据片段 → L3 原始来源（一手/分析/反对） → L4 按需生成深度研究 |
| **回溯** | 沿时间往回：这件事的完整时间线、当时媒体怎么说、我当时的判断是什么 |

### 7.2 有限性信号（对抗沉迷的核心机制）

- 每个 Story 有 `novelty_frontier`：卡片显示 **「已追平最新」**
- 全局有 **「今天的新增已读完」** 标记
- 不给假紧迫感、不自动播放、不做无限视频
- 已读/已知的内容淡化，不重复占据注意力

### 7.3 Web 的九个页面

| 页面 | 内容 | 为什么需要 |
|---|---|---|
| **Stream** | 无限流（故事更新为卡片，三轴下探） | 想看的时候随便看 |
| **Story** | 规范化页面：时间线 + 当前主张集 + 证据 + 复述列表 + 我的标注 | 一件事的完整样貌 |
| **Entity** | 关于某人/公司/产品的一切：事实表（按谓词）+ 历史变更 + 相关故事 + 我的立场 + 我的笔记 | **浏览记忆的主入口** |
| **Topic / Beat** | 覆盖地图：我知道多少、缺什么、源质量如何 | 发现"我不知道自己不知道" |
| **Memory** | capture 浏览：意图/时间/关联实体/复核日，支持 facet | 私人记忆的检索与回访 |
| **Claims** | 冲突 / 未验证 / 过期 / 被推翻 | 数据质量可视化 |
| **Stance** | 我对某实体/议题看法的演化史（带当时依据） | 让"我的观点"成为可回看的记忆 |
| **Search** | 结构化 facet + 语义混合 | "我是不是看过…" |
| **Audit** | 为什么没推 / 我漏了什么 / token 账本 / 源健康 | 失败可见 |

## 8. 记忆：捕获与回访

- **捕获零摩擦**：IM 一句话 / 转发链接 / 语音 / 剪藏。默认进 inbox，Librarian 事后归类。
- **每条记忆记三件事**：内容、**为什么存（意图）**、**什么场景下应该再出现**。第三件决定它会不会变成死库存。
- **意图分类**：参考 / 待读 / 想法 / 决策（带复核日）/ 生活。
- **三种人类问法**：我存过 X 吗（语义+实体）/ 我对 Y 知道到哪（story 聚合水位）/ 这个数字哪来的（claim→evidence→原文）。
- **回访机制**：`review_at` 到点后在简报里出现（"你 3 个月前决定的事，今天到复核期了"）。这是记忆系统真正的价值，不是能存多少。
- **反囤积指标**：保存后 30 天被再次打开的比例。低于阈值说明捕获太廉价/检索太差，要修，而不是继续存。

## 9. 源：可插拔 adapter 契约

```yaml
# adapters/rss-main.yaml
id: rss-main
kind: rss
version: 1
config:
  feeds: [...]          # 或 discovery 路径
  interval_minutes: 30
  fetch_full_text: true
policy:
  max_items_per_run: 200
  rate_limit_rps: 2
```

必须实现四个方法（语言无关，也可直接写 Python 类）：

| 方法 | 契约 |
|---|---|
| `list(cursor) -> [ItemRef]` | 只回元数据与 URL，不保证正文 |
| `fetch(ref) -> RawDoc` | 取正文/字幕/附件；失败要可重试、可区分"永久失败" |
| `normalize(raw) -> NormalizedDoc` | 标题/作者/时间/语言/正文/媒体类型，统一形状 |
| `health() -> Health` | 最近成功率、延迟、配额；用于在 Audit 页显示"源挂了" |

约束：采集层**不能假设一定是文章**——`media_kind` 要能承载 video/podcast/paper/post；`raw_path` 存原文或转写件。

## 10. 标注与学习（你愿意写 comment，这是最值钱的输入）

一次标注做四件事：

1. **推进水位**：`known` → 不再推同类
2. **修正系统**：`wrong` + comment → 降低该 claim 置信度、触发重验证
3. **形成立场**：`agree/disagree` + comment → 生成/修订 `stance`（带当时依据的 claim id）
4. **校准质量**：作为评估系统的 ground truth（每周抽样看"系统判断 vs 你的标注"一致率）

UI 原则：**一键即存，评论可选**。不弹窗、不强制分类、不打断阅读。

⚠️ 待定：comment 要不要成为"可引用证据"（比如你说某 claim 错了，是否直接把它标 contested 并挂你的注释作为一条 evidence）。我倾向**要**，但区分"用户判断"与"来源证据"两种 evidence 类型。

## 11. 技术选型

| 部分 | 建议 | 理由 |
|---|---|---|
| 存储 | **SQLite (WAL) + FTS5 + sqlite-vec** | 单用户、事务一致、可备份、可导出 |
| 正文/媒体 | 文件系统（`data/raw/…`）+ 表内摘要 | 大字段不入库 |
| 嵌入 | 云 API 或本地多语模型 | 中文要好；预算充足可全量 |
| LLM | 可插拔 provider（按任务选模型：抽取用便宜模型，深研用强模型） | 成本与质量分层 |
| 后端 | Python (FastAPI) 或 TypeScript (Hono) 单进程 | 别上微服务 |
| 前端 | 桌面优先的 Web（React/Svelte），移动端只读 | 浏览记忆是桌面行为 |
| 调度 | 容器内调度器（cron 式）+ 事件触发 | 时区固定 |
| IM | Telegram Bot（已有 token）或微信 | 简报最省注意力 |
| 部署 | NAS 上 Docker，本地卷持久化 | 已有环境 |

**降级路径**（预算/限流异常时）：`essential`（采集+去重+简报，不深研）→ `standard` → `deep`。token 账本按 agent 记录，超额时自动降档而不是静默失败。

## 12. Token 预算核算（10B/月 ≈ 333M/天）

以 **2,000 item/天** 为基准：

| 任务 | 量 | 单次 | 日耗 |
|---|---|---|---|
| 嵌入 + 正文归一 | 2,000 | 8k | 16M |
| Claim 抽取（每 item） | 2,000 | 7k | 14M |
| Story Editor（活跃故事 400 × 3 次更新） | 1,200 | 12k | 14.4M |
| Fact Checker（交叉验证+重验证） | — | — | 6M |
| Beat Reporter（50 议题 × 2） | 100 | 20k | 2M |
| Chief Editor（简报） | 1 | 50k | 0.2M |
| Librarian | 1 | 15k | 0.2M |
| 按需深研 | 5 份 | 500k | 2.5M |
| 夜间整合/本体演化/回填 | — | — | 20M |
| **合计** | | | **≈75M/天 ≈ 2.3B/月（占 22%）** |

**余量用来做什么**（这是 10B 换来的真实能力）：

- 源扩到 **10,000 条/天**（≈6B/月）
- **视频/播客转写与理解**（转写单算，理解约 +20M/天）
- **历史全量回填**：把过去几年的邮件/收藏/文档一次性吃进来
- **周期性重验证**：每条 claim 季度复核，"记忆不腐烂"
- **多轮深研**：一次可烧 80 万 token 写一份替代 20 篇报道的整合报告

## 13. 分期

| 期 | 交付 | 验收 |
|---|---|---|
| **P0 记忆底座** | schema + capture（IM 捕获）+ 手工/半自动 claim + Entity/Story/Search 三页 + 导出 | 3 秒记一条；一周后凭模糊描述找到；Entity 页能列出"我知道的一切" |
| **P1 采集与去重** | adapter(RSS/API/manual) + L1/L2 + Claim 抽取 + 证据校验 + Story Editor + IM 简报 | 简报里同一事件只出现一次；每条都答得出"新在哪/为什么推你" |
| **P2 拉与标注** | Web 无限流（三轴下探 + 有限性信号）+ 标注闭环（含 comment）+ Stance | 连续 5 天：冗余率 <5%、信噪比 >60%、能标记"已追平" |
| **P3 主动发现** | Beat Reporter + 覆盖缺口 + 探索槽 + 源质量 + 深研（按需） | 每周至少 3 次"我不知道自己不知道"的发现且你不反感 |
| **P4 长期可靠** | 回填 + 周期重验证 + 本体演化 + Audit 页 + 降级路径 | 3 个月后旧 claim 有过期标记；能回答"我漏了什么" |

刻意不做：实时无限刷新的社交流、多用户、全平台爬虫、替代搜索引擎、engagement 指标。

## 14. 度量

| 指标 | 定义 | 目标 |
|---|---|---|
| 信噪比 | 读完的 / 推送的 | > 60% |
| 冗余率 | 推送中"已知且零新增" | < 5% |
| 漏报抽检 | 每周抽 3 个热点，看是否覆盖或明确判定不值 | 0 次"该知道我却没有" |
| 追平率 | Web 上点开的故事里"已追平最新"的比例 | > 50%（说明系统真在帮他收敛） |
| 深探使用 | 展开到 L3/L4 的比例 | > 10%（说明深度有价值，且没滥用） |
| 标注消费率 | 你的 comment 被后台采纳（改了 claim/stance）的比例 | > 80% |
| 捕获回收率 | 保存内容 30 天内再次被打开/引用 | > 20% |
| 记忆召回 | "我记得看过…" 查得到 | > 80% |
| 时间账 | 每天实际花费 | 稳定在预算内 |

**注意**：如果它让你花的时间变多，它就失败了——哪怕内容更"优质"。所以没有"使用时长"指标，只有"追平"和"时间账"。

## 15. 风险

| 风险 | 表现 | 对策 |
|---|---|---|
| 无限流成瘾 | Web 变成刷不完的信息流 | 有限性信号 + 三轴下探 + 无 engagement 指标 |
| 幻觉进记忆 | 你以为知道，其实是模型编的 | 子串证据校验 + `unverified` 状态 + 周期重验证 |
| 本体过度膨胀 | 谓词越来越多、越来越乱 | 谓词需批准；定期废弃；退化到自由文本 |
| 抽取过细 | 每句一条 claim，噪音爆炸 | 粒度按"可独立陈述且可验证"定义，先粗后细 |
| 成本/账单单点 | 某 agent 跑飞 | token 账本 + 单任务上限 + 自动降档 |
| 过滤器黑箱 | "凭什么不推" | decision_log 可查 + Audit 页 |
| 维护腐烂 | 抓取挂了没人知道 | 源健康检查 + "今天 0 条"必须告警 |
| 茧房 | 越用越窄 | 探索槽 + 必达通道 + 兴趣体检 |
| 合规 | 付费墙/版权 | 只接提供 RSS/API 的源；默认存引用与摘要，全文可选 |

## 16. 还差你拍板的（其余已定）

1. **源的初始清单**：先接哪 3–5 个？（RSS / Newsletter / 特定站点 API / 手动转发）
2. **视频与播客**：要不要转写？（要的话 P1 之后加 Whisper 工序，成本另算）
3. **claim 粒度**：句级（查得细、噪音多）还是段级（干净、但会漏）？我建议**句级抽取 + 页面按主题聚合**。
4. **我的 comment 是否可作证据**：我建议要，但与"来源证据"分类型。
5. **部署与访问**：内网 only，还是手机在外也要能开（决定认证/反代）？
6. **简报节奏**：每天几点、几条？（默认 08:00 / 12 条）
7. **语言**：中文为主，英文源要不要自动翻译成中文？
8. **Web 前端栈**：有偏好吗？（无偏好我选 SvelteKit 或 React+Vite，桌面优先）
9. **起步数据**：要不要一次性回填历史（邮件/收藏/过往笔记），还是从今天开始？

## 17. 与现有系统的关系

- **ai-memory**（已有）：给 **agent** 的跨会话记忆，服务对象是 AI。本系统服务对象是**你**，不进同一套数据。可共用 NAS/Docker，可互相引用（简报里引用你存过的结论）。
- **DSH**：可作为 "工人"（跑抽取/写简报的 agent），但数据主人是这套系统自己的 SQLite。接口化，不硬绑。
- 开源参考：[cruxwire](https://github.com/philoking/cruxwire)（RSS + 本地 LLM 打分聚类去重）、[mimir](https://github.com/sp1r1t/mimir)（多源 + 兴趣画像 + 同事件 story 合并）。**它们停在 documents 聚合层**，没有 claim 差集、没有知识水位、没有立场对象——这三件是本系统的核心差异。
