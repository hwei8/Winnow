## 3. 质量实测：三个必须正视的问题

### 3.1 ASR 对技术术语的损坏是**双峰分布**的

按"每千字异常拉丁 token 数"统计：

| 分位 | 值 |
|---|---|
| 中位数 | 0.6 |
| 最差 8 个 | 11–15.5 |

也就是说：**普通口播基本可用，但双语技术视频（恰好是你最关心的那类）损坏严重**。真实样本（BV11NRzB9E51，llama.cpp 混合推理）：

| ASR 输出 | 实际应是 |
|---|---|
| `LAMOS VP` | llama.cpp |
| `编议选项` | 编译选项 |
| `7900差地差` / `C900XTX` | 7900 XTX |
| `张亮并行` | 张量并行 |
| `AK` / `NK` | A 卡 / N 卡 |
| `2006年5月4日` | **2026** 年 5 月 4 日 |
| `平辆导弱` | 平台导入 |

**结论：ASR 文本不能直接进 claim。** 尤其数字和专有名词——它们恰恰是 claim 的核心内容。

### 3.2 语言与标点

- **38/147** 个视频的转写以**繁体**为主（Whisper 语种/字形漂移），同一批数据里繁简混排。
- **135/147** 几乎没有标点（ASR 原样输出，靠空格分词）。

→ 需要统一工序：繁→简 + 标点恢复，否则句子级切分和检索都会崩。

### 3.3 旧摘要质量参差（你说得对）

`detailed_summary / 转写字数` 的比例：**p10 = 0.20，p50 = 1.16，p90 = 2.69**，有 3 个是 0（空摘要）。
不同 LLM + 不同 prompt 的产物混在一起，且**无法追溯每篇是哪个模型写的**。

→ 处理原则：**旧摘要一律降级为"历史解释（hint）"，不作为事实来源**。事实只能从转写重新抽。

### 3.4 缺件

- 3 个目录残缺：1 个空目录、1 个只剩 `.part` 下载残片、1 个空
- 10 个缺 `metadata.json`
- 12 个没有截图帧

→ 回填时要能"部分导入"，不能因为缺一个文件就整条丢弃。

## 4. 意外发现（这条最重要）

### 4.1 截图帧与转写段落是**一一对应**的，而且画面里有**烧录字幕**

- `帧/段落` 比例：中位数 **1.00**；138 个有效视频里 **60 个严格接近 1:1**（p10 0.19 的那批是抽帧失败）
- 帧文件名 `transcript_0038_89.580.jpg` = 第 38 段、89.58 秒 → **可精确反查是那句话对应的画面**
- 实测画面内容：屏幕录制 + **底部烧录的中文字幕** + 画面上的代码/幻灯片/图表

我在 BV11NRzB9E51 的 `transcript_0038_89.580.jpg` 里肉眼读到了字幕「应该也不用进行对比了」，而同一位置的 ASR 是「应该也不用进行对比了」——这条是对的；但画面里同时有 `llama.cpp` 的清晰字样，而 ASR 把它听成了 `LAMOS VP`。

**这意味着：42,001 张帧 = 一个可 OCR 的"视觉字幕库"，能用来纠正 ASR 的专有名词/数字错误，并给 claim 提供视觉证据。**

### 4.2 旧摘要的时间戳 98.4% 能对齐到转写段落

`key_topics[].timestamp` 落在某个转写段落起点 ±6 秒内的比例：**1196/1215 = 98.4%**（覆盖 138 个视频）。

→ 旧 `key_topics` 可以直接当**初版 Story 时间线 / 章节骨架**，省掉一次重建；但内容要重写。

## 5. Claim 粒度实验（用真实数据回答"claim 力度"）

拿 BV11NRzB9E51（3 分 54 秒，92 段）做三档对比：

### 档 A：段级（每个 ASR 段 = 1 条）

92 段 / 4 分钟 ≈ **23 条/分钟**。内容如：
- 「到好啊现在是2006年5月4日的晚上11.35分」← 无信息
- 「路这个视频呢是书接上文」← 无信息
- 「应该也不用进行对比了」← 无信息

→ **不可用**。段级只能做证据索引，不能做记忆单元。

### 档 B：原子事实级（**建议**）

同一份内容抽出 **9 条**，密度 ≈ **2.2 条/分钟**：

| # | Claim | 类型 | 时间范围 | 证据 |
|---|---|---|---|---|
| 1 | llama.cpp 新增编译选项，同一可执行文件同时支持 ROCm 与 CUDA 后端 | fact | 00:06–00:16 | 段 2–3 + 帧 transcript_0002 |
| 2 | 测试平台：2× RTX 3070M + 1× Radeon 7900 XTX(24GB) | fact | 00:30–01:00 | 段 8–10 |
| 3 | 35B 模型：prefill ≈1300 tok/s、decode ≈50 tok/s | number | 01:01–01:33 | 段 14–20 |
| 4 | 7B 模型：prefill ≈600 tok/s、decode ≈15 tok/s | number | 01:01–01:33 | 同上 |
| 5 | A+N 混推不走网络，不受 RPC 带宽/延迟限制，仅受 PCIe 带宽限制 | fact | 01:32–02:06 | 段 21–27 |
| 6 | 7900 XTX 价格约 5000 元，用 A 卡扩显存性价比不高 | number/评估 | 02:41–03:12 | 段 60–70 |
| 7 | 混合推理只能流水线并行，无法张量并行 | fact | 03:43–end | 段 90–91 |
| 8 | 实际意义仅限"手里已同时有多种卡"的人 | opinion | 03:11–03:43 | 段 85–89 |
| 9 | ⚠️ 测试模型型号（"1.5RTB/1.535B A3B"）ASR 损坏，需 OCR/元数据校正 | 待定 | — | 低置信 |

**密度推算**：35.7 小时 × 2.2 条/分钟 ≈ **4,700 条 claim**。这个量级对 SQLite 和人工审阅都完全可控。

**判定标准**（写进抽取 prompt）：
> 一条 claim 必须 (a) 能被独立陈述，(b) 能被证据片段验证或反驳，(c) 去掉它你会丢失信息。
> 三者缺一，就不是 claim——是语气词、过渡句、或者评论区的话。

### 档 C：主题级（= 旧 summary 的 key_topics）

5–7 个章节 / 视频。→ 这是**页面组织单位**，不是记忆单位。

**结论：Claim = 档 B（原子事实），Evidence = 段 + 帧，页面 = 档 C。** 三档各有其位，不冲突。

## 6. 回填方案（新增 adapter: `dossier`）

### 6.1 字段映射

| 源资产 | 落到新系统的哪 |
|---|---|
| `metadata.json` | `source`（up主→entity，tags→topic，发布时间→`published_at`，播放/点赞/评论→排序特征） |
| `transcript.json` | `item.extracted_text` + `item_segment[]`（段级时间戳，**视频源的一等公民**） |
| `frames/` + `frames_manifest.json` | `frame`（与 segment 关联）+ OCR 文本 → 用于纠错与视觉证据 |
| `summary.json` | `story.seed`（历史解释，`extraction_method='legacy-llm'`，置信度上限设 0.4） |
| `article.md` | 同上，作为人类可读的历史速览 |
| `report.html` | 抽取正文 → 文本后**丢弃**（1.6GB） |
| `audio.wav` | 转码为 opus 后**丢弃原文件**（18GB → ~70MB） |
| `video.mp4` | 可选：保留用于时间戳跳转验证；或只保留 ≤720p（9.6GB → ~2GB） |

### 6.2 三步走

1. **结构化导入**（无 LLM）：metadata → source/item；transcript → segment；frames → frame 索引；生成 `item` 记录与资产清单。
2. **重加工**（LLM，全量）：繁→简 → 标点恢复 → **OCR 帧字幕并做术语纠错** → 抽 claim（档 B） → 实体/谓词归一 → 与旧 `key_topics` 对齐生成 Story 骨架。
3. **质量分级**：每条 claim 打 `confidence`，证据不足的进 `unverified`；ASR 损坏段标 `asr_quality: low`。

### 6.3 成本估算（有 10B 就不必省，但要知道量级）

| 工序 | 量 | token |
|---|---|---|
| 全量转写重读 + claim 抽取 | 1.27M 字 ≈ 0.9M token | 抽 3 遍 ≈ **5M** |
| 旧摘要对齐/重写 | 147 × 5k | 0.7M |
| OCR（42k 帧） | 42k 次视觉调用（可只对字幕区域裁剪+批量） | 另计，量大但可抽样 |
| 全量第一次回填合计 | — | **约 10M token 量级（半天内跑完）** |

对比 10B/月 的配额：**回填只占 0.1%**。所以正确策略不是"省"，而是"跑三遍、互相校验"。

### 6.4 存储瘦身

| 项 | 现状 | 处理 | 处理后 |
|---|---|---|---|
| audio.wav | 18 GB | 转码 opus 后删 | ~0.07 GB |
| report.html | 1.6 GB | 抽文本后删 | ~0 |
| video.mp4 | 9.6 GB | 可选：保留 / 720p / 全删 | 0–2 GB |
| frames | 5.6 GB | 可选：转 webp 720w | ~1.7 GB |
| 其它（json/md） | ~0.5 GB | 保留 | 0.5 GB |
| **合计** | **36 GB** | | **约 2–4 GB**（保留视频则 11–14 GB） |

## 7. 对设计的四点影响

1. **`claim_evidence` 要支持"介质证据"**：视频源的证据不是"字符偏移"，而是 `(segment_idx, time_start, time_end, frame_path, frame_ocr_text)`。`SCHEMA-DRAFT` 需要加这一层（原设计只写了 char offset）。
2. **`item` 要加"转写质量"字段**：`asr_quality_score`、`script`（简体/繁体）、`punct_restored`、`ocr_corrected`。否则你永远不知道某条记忆基于多烂的输入。
3. **"旧摘要"要作为一等对象保留**：不是事实，但是**历史解释**（"2026 年 5 月，某个模型是这么总结这件事的"）。它本身有考古价值，也是模型质量的对照基线。
4. **回填要提到 P0**：这是你唯一已有的真实语料，且足够验证 claim 抽取/去重/浏览三条链路。B 站实时采集（用户说 tricky、先不急）可以后置。

## 9. 附：B 站采集的 "tricky" 点（供以后，现在不展开）

- 需要 WBI 签名 / cookie（SESSDATA），无 cookie 易触发风控
- 字幕接口对部分视频不返回；CC 字幕质量参差
- 音频下载要处理分 P、多码率、referer
- 限流严格，批量抓取需要控制节奏与失败退避
- 版权：只存引用/摘要与必要片段，不对外分发

这些等你决定接 B 站时再处理——**好消息是：上面这批数据已经把"转写 → claim → Story"整条链路的验证材料给你了，不依赖新采集。**
