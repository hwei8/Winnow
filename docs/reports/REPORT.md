# P0 技术验证报告 — 记忆底座

> 目标：用 `Summary` 的 150 个视频资料库（不改动源数据），验证"记忆底座"的核心假设：**结构化 + claim 级 + 证据链 + 可查询** 是否成立，以及在 100 万条 claim 规模下的性能。
> 位置：`<old-repo>/memory-p0`（独立于设计文档与源数据）
> 结论：**底座成立，但有两处设计需要修正（词面去重不可用、聚类判据要改）。**

---

| 成本 | 1.62M tokens（82 items，含 reasoning）≈ **19.8k tokens/条视频** |

**质量抽查（30 条随机 claim 对证据，LLM 判定）**

| 判定 | 数量 |
|---|---|
| supported（证据直接支持） | **28** |
| partial（需常识补全） | 2 |
| unsupported（幻觉/矛盾） | **0** |

**样本（BV11NRzB9E51，3 分 54 秒 → 15 条 claim）**

```
1.  [6-13s]   5月2日发布的视频《多后端加载机制解析》讲解了 llama.cpp 新增的编译选项。
2.  [13-18s]  添加该编译选项后，编译得到的 llama.cpp 可以使用 A 卡推理模型。
4.  [28-41s]  网友的测试使用两张 3070M N 卡和一张 7900 XTX A 卡进行混合推理。
6.  [57-63s]  A 卡和 N 卡混合推理不必再借助原来的 RPC，因此不受网络带宽和网络延迟影响。
7.  [67-73s]  35B 模型的预填充速度约为 1300。
13. [165-169s] 7900 XTX 的显存容量为 24GB。
14. [177-180s] 一张 7900 XTX 的价格约为 5000 元。
15. [222-230s] A 卡和 N 卡混合推理只能采用流水线并行，无法使用张量并行。
```

对照人工抽取的 9 条：机器版更细（15 条），关键数字、结论、时间点全部命中，量级一致。

**发现的问题**

1. **长视频不能单次抽取**：reasoning 会把 `max_tokens` 吃光导致空输出。必须分块（约 5k 字/块）+ 20k 输出上限。这是本次最耗时的工程修正。
2. **数字缺单位**：`35B 的预填充速度约为 1300` —— ASR 原文就没说单位，claim 只能照抄。26 条 number 类 claim 里不含数字，需专门规则。
3. **元信息混入**：`5月2日发布的视频讲解了…` 属于"上期回顾"而非事实，需要过滤规则（"本视频/上期/下期"）。
4. **外语视频**：日文/英文视频需翻译统一成中文，否则跨语言去重和检索都失效。

## 6. 结果 D：去重 / 复述率（需求 3 的验证）

**测试方法**：8 个多条目 Story，交叉条目共 **30,345 对** claim；两条路——① 词面 trigram 相似度检测 ② 随机抽样 80 对让 LLM 判定是否"同一事实"。

| 路径 | 结果 |
|---|---|
| 词面 @0.45 候选 | 7 对；LLM 判定真重复 **2 对** → **precision 0.29** |
| 随机抽样 80 对 | LLM 判定重复 **0 对** → 真实复述率 **< 3.7%**（95% 置信上界） |

**判读（重要，需要修正设计）**：

1. **词面相似度不能用于 claim 去重**：改写（paraphrase）几乎必然漏检，而命中的多是巧合。**必须 embedding 召回 + LLM 裁决**。
2. **本数据集的 claim 级复述率极低**，但不是因为"去重做得好"，而是内容类型决定的：

```
Story「MTP 加速 Qwen 模型」两个视频的 claim（实测）：
 A 视频：122B Q4 开 MTP 接受率 88%、32 token/s；MTP 层量化后 1.63GB；3090 上 27B Q8 约 17 token/s
 B 视频：MTP + TurboComb 显存 27G→23G；4090 上 45→75 token/s；不用 MTP 会 OOM
```

两条视频讲同一件事，但**数字、硬件、结论完全互补**——claim 层几乎零重叠。

3. **结论修正**：所谓"一个热点出上千篇" 的冗余，在**解释类内容**里主要发生在 **story/标题层**（已经由 Story 聚类解决），claim 层去重对**新闻通稿类**内容才关键。P0 这个数据集验证不了新闻型冗余，**需要等 B 站/新闻源接入后重测**。

- **SQLite 在 100 万 claim 下没有崩**：所有查询仍在 0.5s 内，个人应用可接受。

  1. `story` 表冗余维护 `last_update_ts / new_claim_count` → Q3 变成索引查询（预计 <1ms）

## 8. 结论：哪些设计被验证，哪些要改

### ✅ 被验证

1. **结构化底座成立**：item/segment/frame/story/claim/entity/topic 七张主表能承载这批数据，导入成本可忽略。
2. **原子事实级 claim 是正确的粒度**：1.8 条/分钟、22 条/视频，人工可读、机器可查、去重可算。
3. **类型化（subject/predicate/object）比预期可行**：47% 自动抽出，说明不必等本体完全设计好再开工。
4. **证据链是这套系统的护城河**：100% 可溯源 + 0 幻觉抽样，意味着"记忆"可以被核验，而不是只能相信。
5. **截图帧是有价值的证据层**：67% 的 claim 能配上对应画面，OCR 纠错和"跳回去看"都成立。
6. **SQLite 够用到百万级**，且退化点明确、修复便宜。

### ⚠️ 必须修正

1. **去重不能靠词面相似度**（precision 0.29）：改为 embedding 召回 + LLM 裁决，并把"同一事实"判定做成可缓存的结构化结果。
2. **Story 聚类判据要改**：从"主题相似"改为"同一具体事件"，否则 6 个同主题视频会被合成一个假事件。
3. **长内容必须分块抽取**：单次调用会被 reasoning 挤爆，且必须校验 `finish_reason`。
4. **数字/单位需要专门归一化**：`object_value` 应结构化（值+单位+口径），否则"1300"没有意义。
5. **元 claim 过滤**：上期回顾、订阅引导、"本视频"这类要规则排除。

### ❌ 本次无法验证（需要后续数据）

- **新闻型内容的高复述率**：需要接新闻源才能测 claim 层去重真正的收益。
- **跨视频的"已知水位"**：需要人工标注已知水平，本次未做。
- **OCR 纠错效果**：42k 帧还没跑 OCR，下一轮验证。

## 12. P0.1 修正与复验（2026-11-10）

按 P0 报告列出的 5 个问题逐条修复并复验。

### 12.1 聚类判据：从"主题相似"改为"同一具体事件"

改动：`02_cluster.mjs` 改为**全局单次聚类**（避免分批断裂），每个簇必须给出 `anchor`（共用的事实锚点）；新增 `02c_validate.mjs` 对每个多条目簇做审计，判为 `mixed` 的按真实事件拆开。

结果：

| | P0 | P0.1 |
|---|---|---|
| Story 总数 | 128 | **141** |
| 多条目 Story | 8 | **1** |
| 最大簇 | 6 个视频（Harness Engineering） | 2 个视频 |

原先"6 个 Harness Engineering 视频合成一个事件"是**主题相似**造成的误聚，复验后被拆开。

**由此得到一个重要的数据结论**：这批语料**几乎没有"同一事件的多源覆盖"**（142 个视频 → 141 个事件）。所以 claim 级去重在这批数据上**没有真实收益可测**——去重机制只能用合成控制组验证，等接入新闻源再实测。

### 12.2 元信息过滤

规则正则（本视频/上期/订阅/点赞/三连/片尾…）同时作用于抽取 prompt 与落库后处理。当前 24 条被标记 `is_meta=1`、`status='meta'`，Web 查询默认排除。

### 12.3 数字结构化：一次真实的数据完整性事故

第一版归一化按"数组下标"对齐 LLM 返回，结果**值被错配到别的主张上**：

```
错误：'600多名驾驶员中有260多名获奖…'  →  {num:300, unit:'元', qualifier:'三百到四百元'}
```

原因是模型返回的数组长度/顺序与输入不保证一致，而我又没有校验。改成 **ID 键控 + 数字存在性校验**：
- 每条回传原 `id`，按 id 匹配，不按下标
- 抽出的 `num` 必须在原文数字集合里（允许"一两百→100/200"这类口语近似）
- 对不上就**不写**（宁缺勿错）

结果：**400/522 条数字类 claim 结构化成功，119 条因数字对不上被拒绝**。示例：

| claim | 结构化值 |
|---|---|
| 7900 XTX 的显存容量为 24GB | `{num:24, unit:"GB", qualifier:"显存容量"}` |
| 一张 7900 XTX 的价格约为 5000 元 | `{num:5000, unit:"元", currency:"CNY"}` |
| EUV 光刻的墙插效率低于 0.1% | `{num:0.1, unit:"%", qualifier:"低于"}` |

### 12.4 分块抽取加固

加了 `finish_reason` 校验、半段重试、更小块兜底。全量补齐结果：

| 项 | 值 |
|---|---|
| 完成条目 | **142 / 142，0 失败** |
| 本轮 60 条耗时 | 2,274s（约 38 分钟） |
| 本轮 token | 2,084,352 |
| 全库 claim | **3,778**（26.6 条/视频，1.76 条/分钟） |

### 12.5 去重：多路召回 + LLM 裁决

LLM 网关没有 embeddings 端点（实测 `POST /embeddings` → 404），所以用多路结构召回替代向量召回：

| 召回路线 | 候选数 |
|---|---|
| 词面 trigram ≥0.35 | 12 |
| 同 subject+predicate | 2 |
| 共享显著数字 | 1,478 |
| 共享实体 | 3,215 |
| **合计 → 限流后送审** | **4,707 → 134** |

裁决结果：

| 项 | 结果 |
|---|---|
| 真实数据 | 134 对送审 → **1 对判为重复**（两个视频里逐字相同的 claim） |
| 阴性对照 | 6 对已知不同 → **全部判 false**（无假阳性） |
| **合成控制组**（20 条真实 claim 的改写） | **召回 16/20 = 80%**，其中 16 条词面路由就能覆盖 |

**结论**：LLM 裁决可信（0 假阳性、80% 召回），但**召回瓶颈在候选生成**——4 条改写未被词面路由覆盖。生产环境必须补 embedding 一路召回（要么换有 embeddings 的 provider，要么本地跑一个小嵌入模型）。

## 13. 附：OCR 纠错抽样实验（P0.2 预研）

完整记录见 [OCR-FINDINGS.md](OCR-FINDINGS.md)。一句话结论：**能读出烧录字幕，但不能直接拿帧去对齐 ASR。**

- 126 帧抽样（21 个视频，ASR 质量三档）：OCR 成功 126/126，检出字幕 79.4%
- 与 ASR 滑动窗口对齐 ≥0.8 的只有 **22%**；<0.5 的占 **59%**
- 但确实能纠错：`VA2→VAR`、`CD密药→CI/CD 密钥`、`合犯算买机→盒饭贩卖机`；与 ASR 完全一致的对照组也命中
- 对不上的主因：字幕跨度 ≠ ASR 段跨度、帧与字幕有时间差、模型会读画面上的其他文字（"防走丢/防眩光"）、部分视频根本没有烧录字幕

**结论**：帧用于"视觉证据 + 人工核验"成立（69.5% claim 已配帧）；"自动 OCR 纠错"需要独立管线（裁字幕条带 → 字幕存在性判别 → 全局时间轴对齐），不是现成能用的。成本参考：约 992 tokens/帧。
