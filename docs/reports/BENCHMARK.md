# 决策点 Benchmark：Jev vs opencode LLM judge

> 目标：把"判定类"工作全部换成 Jev（决策模型）后，验证**质量不掉、成本大降**。
> 方法：同一份带标签样本、同一任务描述，分别跑 Jev（`~typesafe/jev-latest`，noul/choice）与 opencode（deepseek-v4.1-flash，聊天 + JSON），比较 P/R/F1 与成本。

## 总表

| 决策点 | 样本 | Jev 最优 | opencode 基线 | 结论 |
|---|---|---|---|---|
| **claim 去重**（同事实？） | 45 对（21 同义改写 + 24 负） | **F1 = 1.000**（阈值 0.4–0.7） | F1 = 0.976（P 1.0 / R 0.952） | Jev 略优 |
| **事件同一性**（同一件事？） | 88 对（63 事件内 + 25 随机） | **P 1.000 / R 0.905 / F1 0.950**（阈值 0.5） | P 1.000 / R 0.429 / F1 0.600 | **Jev 召回是 opencode 的 2.1 倍，零假阳性** |
| **新旧冲突**（同一属性不同值？） | 28 对（14 构造矛盾 + 14 改写） | F1 = 0.759（P 0.733 / R 0.786） | **F1 = 0.833**（P 1.0 / R 0.714） | opencode 精度更好，Jev 召回更好；Jev 需调 criteria |
| **时效分类**（8 类） | 40 条 | 与 opencode **一致率 55%** | — | 类别边界本身未定义清，暂不能算"通过" |

**成本**：Jev 全流程（事件/去重/冲突/时效/评分/粒度实验）合计约 **$0.174**；单次判定成本 **$0.0076 / 千次**。opencode 侧仅成本体现在订阅内，本轮 benchmark 消耗约 13 万 token。

## 1. claim 去重（Jev 满分）

- 正样本 = 20 条 claim 的"同事实不同措辞"改写；负样本 = 25 对随机 claim。
- Jev 阈值 0.4–0.7 全部 **P=1.0、R=1.0**；阈值 0.8 时 R=0.952。
- opencode 同集合：P=1.0、R=0.952、F1=0.976。
- 全库 5,618 条 claim → 2,934 个候选对 → 送 260 对判定 → **4 对重复**（含 1 对完全相同的 claim、1 对仅少"最终"二字、2 对语义重复）。

## 2. 事件同一性（Jev 可用）

- 干净标签集（63 事件内对 + 25 随机对，5 组：Val Town / Gemini 4 Carbon / Walliams / Krakow / Anthropic IPO）：阈值 0.5 时 **P=1.0、R=0.905、F1=0.950**；阈值 0.8 时 P=1.0、R=0.762。
- opencode 同集合：P=1.0、**R=0.429**、F1=0.600——同一份任务描述下，聊天模型漏掉了一半以上的同事件对。
- 全库 395 条新闻 + 260 个候选对：13 个事件簇（38 条），其中 **5 个跨源簇**（Nvidia 丑闻 7 篇横跨 NYT+Verge；Fable 5.2 6 篇横跨 HN+cnBeta；Starlink Mini 2、Ableton Live 13 横跨 Verge+HN）。
- ⚠️ 说明：另一次把"同主题标题"全标成"同一事件"的 benchmark 不可用——它把同一丑闻下的多个子事件（股价、中国回应、雇佣律所）都标成"同一事件"，标签本身有噪声；因此以 63+25 的紧凑标定集为准。

## 3. 新旧冲突（Jev 不如 opencode 精度，需调 criteria）

- 构造集：14 对"同一 claim 改掉核心数值"（真矛盾）+ 14 对"同事实改写"（非矛盾）。
- Jev 最优在阈值 0.5：P=0.733 / R=0.786 / F1=0.759；阈值 0.8：P=1.0 / R=0.357。
- opencode：P=1.000 / R=0.714 / F1=0.833。
- 真实数据（92 对同主语同谓词不同值）：阈值 0.6 下 **1 对真冲突**——"她回忆了婆婆遭暗杀一事" vs "她回忆了丈夫遭暗杀一事"（Sonia Gandhi）。
- 结论：**Jev 有假阳性**（把"数值不同"当成矛盾，即使属性不同）；需要把 criteria 收紧到"同一属性"并要求给出属性名。这是 criteria 工程问题，不是 Jev 能力问题。

## 4. 时效分类（类别边界未定义清）

- 8 类：definitional / durable / state / event / measurement / periodic / prediction / opinion。
- Jev vs opencode 40 条一致率 **55%**，分歧集中在 `definitional` ↔ `durable`：
  - 「如果服务过载，返回 429，WKS 会等待并遵守 Retry-After。」Jev=definitional，OC=durable
  - 「DeepSeek V4 是 1.6 万亿参数的大模型。」Jev=state，OC=measurement
  - 「历史上有许多技术虽然在技术上更优，但在商业上却落后了。」Jev=opinion，OC=durable
- 说明：**类别定义本身模糊**（"协议行为规则"算定义还是慢变属性？"模型参数量"算状态还是测量？）。在边界定义清楚前，不应把分类结果当可靠标签用。
- 全量已跑（5,586/5,618 条），分布：event 28%、definitional 17.8%、state 16.8%、opinion 11.8%、measurement 9.6%、durable 9.2%、prediction 4.7%、periodic 2.1%。
- **Strix Halo 类例子验证通过**：「35B 模型的预填充速度约为 1300。」→ `measurement` + `condition_scoped`（记录为真、不外推到别的条件），正是想要的语义。

## 5. 成本与延迟

| 项 | 值 |
|---|---|
| Jev 单价 | $0.042 / 1M 输入 token，输出免费 |
| 单次判定（含 state） | 约 $0.0076 / 千次判定 |
| 全量时效分类（5,586 条） | **$0.136**，71 秒 |
| 全量条目评分（537 条） | $0.006，6 秒 |
| 事件聚类（260 候选对） | $0.018，9 秒 |
| 去重判定（260 候选对） | $0.003，4 秒 |
| 对照：错误地走 jev-router（一次） | $0.21（贵 9 倍，且用错模型） |

## 6. 结论

1. **事件同一性、claim 去重 → 可以放心交给 Jev**（零假阳性，成本可忽略）。
2. **冲突判定 → Jev 需要更严的 criteria**（要求"同一属性 + 互斥值 + 属性名"），否则假阳性偏高；opencode 在精度上仍然更好。
3. **时效分类 → 先定义类别边界**，再谈用谁；当前一致率 55% 说明 rubric 本身没收敛。
4. 判定类任务全部走 Jev 后，成本从"订阅内不可控"变成"可计量的一分钱级"，且结果可复现（温度固定、无自由文本）。
